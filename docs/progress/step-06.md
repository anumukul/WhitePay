## Durable state and spend controls

- Per-chain/account PostgreSQL advisory lock serializes workers; global digest uniqueness prevents double-processing the same signed order across accounts. Tracking uses full digest including payer, not global orderId.
- Conservative reservation commits before signing: approved gas limit \* max fee + L1 reserve. Checked against account balance, all outstanding reservations and UTC-day budget. Actual send encodes explicit L2 caps.
- Exact signed bytes/hash persist before network send, with compare-and-set protection. Both initially signed and recovered bytes must recover the relayer and match approved unsigned hash. Stored raw bytes remain only in PostgreSQL, never logs/reports/CLI arguments.
- Broadcast ambiguity is recorded before RPC; a timeout never releases funds or invents a new nonce. Recovery resends only the identical signed bytes. A separate Node-process test recovers without the original signer.
- Pending nonce mismatches block initial submission. Known mined/unconfirmed transactions wait for receipts. Unknown consumed nonce quarantines; expired ambiguous send retains its reservation. A never-broadcast expired reservation can release safely. Day rollover and tighter current limits require review.
- Actual signed-byte oracle quote is rechecked before broadcast. L1 fees are variable and not protocol-capped; reserve is a safety margin, not a hard L1 maximum. Actual receipt L2+L1 debit replaces reservation and governs subsequent budget admission.
- Canonical two-confirmation RPC receipt, hash, status, gas caps, full PaymentSettled fields and exact token-transfer routing are checked. Revert cannot settle; missing/mismatched event quarantines. API remains submitted for Step 07's indexer/fulfillment authority. No fabricated success payment row or webhook.

Daemon is preview-only and cannot load a private key, sign or broadcast. New library execution requires exact per-transaction approval binding chain, relayer, checkout, orderDigest and unsigned payload hash, plus operator-injected signer. No passwords/seed phrases/keystore contents were requested or used. A generic autonomous funded signer deployment is not approved or claimed.
